# restful-booker 接口自动化测试

![CI](https://github.com/jxyyxxx/restful-booker-api-test/actions/workflows/ci.yml/badge.svg)

- 仓库地址：<https://github.com/jxyyxxx/restful-booker-api-test>
- 在线 Allure 报告：<https://jxyyxxx.github.io/restful-booker-api-test/>

这个仓库是我给开源的 [restful-booker](https://github.com/mwinteringham/restful-booker) 做的接口自动化测试。被测系统不是我写的——Node.js + Express + LokiJS 内存库，8 个接口；我写的是测试侧：七层框架、40 条用例、Allure 报告体系、GitHub Actions 流水线。

动手之前我给自己定了三个标准：用例要能证明自己有效，功能坏了它得红；报告要能直接分流，失败时一眼看出该找开发、查部署还是查性能；流水线要能复现，同样代码跑两次结果得一样。后面的设计基本都是围绕这三件事做的取舍，不是为了把功能堆齐。

框架按七层分：配置、工具、接口方法、数据、用例、夹具、入口。分的依据不是功能齐全，是哪类东西会变就隔一层——接口路径变只改 `api/`，断言规则变只改 `assert_utils`，数据变只改 YAML，用例本身几乎不动。代价也很直接：读一条用例要跨两三个文件，40 条以内其实偏重，如果只有 5 条用例这套就算过度设计。我判断它划算，是因为这个项目会持续加用例、会换环境、要有人接手。

用例 40 条，32 条参数化加 8 条独立，覆盖正常流、参数缺失、未授权和 ID 边界，每条数据对应一个独立场景，不用重复数据凑数。冒烟挑了 6 条，只覆盖「`/ping` → 登录 → 查询 → 修改 → 删除」这条主干；`smoke` 标记只打非参数化函数——登录那个函数展开就是 14 条，整个函数打上标记，冒烟就废了。代价是反向场景进不了冒烟，只能等全量。

测试数据全部自己造，不依赖服务启动时的种子数据，否则换个启动方式就会出现"ID=1 查不到"的假失败。回收有三条路：夹具 `yield` 后置、创建用例 `finally`、会中断的用例兜底再删一次。不回收的后果是可算的——每轮堆 13 条（7 条创建 + 6 条夹具/自建），`GET /booking` 的响应体越来越大，后面的用例和压测都会被污染。

报告是这次花力气最多的一块，也是我觉得最值得看的部分。Allure 默认只有一屏"通过/失败"，我用它做了五件事：环境面板、失败分类、趋势、归档、运行器。

环境面板记 12 个字段——env、base_url、scope、markexpr、collected、Python 和 pytest 版本、操作系统、时延门限、框架自己的 commit、运行时间。其中 `scope` 和 `collected` 是区分"这次跑的是冒烟还是全量"的唯一标识：PR 报告和 push 报告长得一模一样，就靠这两个字段分。`framework_commit` 解决的是另一个问题——用例突然红了，是被测服务改版、还是我把用例改坏了，看一眼 commit 就能分流。

失败分类把 failed / broken 归成三类，而且互斥：响应时间门禁超限、被测服务不可用、断言失败。三类对应三种动作——查性能、查部署、找开发。这里的关键不是"能分类"，是"不能分错"：时延断言抛的也是 `AssertionError`，最初所有时延失败都进了"断言失败"，值班的人会去改代码而不是查性能。修法是时延规则放最前，再给"断言失败"加一条负向断言把时延失败排除掉。

CI 用的是 GitHub Actions。PR 跑 6 条冒烟，push 和定时跑全量；被测服务锁 commit、依赖走 `requirements.lock`，避免上游一动流水线就随机变红；跑之前从 `gh-pages` 把上一份 history 拉回来，不然每次 CI 都是首次运行。报告只发布 `main` 上的全量结果，PR 和手动冒烟不覆盖线上，另外配了 `concurrency`，同分支连续提交时取消旧流水线，避免两份报告互相覆盖。

还有一件不在报告里、但我觉得挺值的设计：给每个关键请求加了 500ms 的时延门禁。它不是性能测试，是在功能回归里顺手拦一道劣化——某次改动让查询从 5ms 变 800ms，功能断言全绿，门禁会红。阈值取本地实测（2~20ms）的 25 倍以上，既不误报抖动，又能抓住真正的退化；调门限不用改代码，环境变量 `RESPONSE_TIME_LIMIT` 覆盖。

改的过程中踩过几个坑，都是改了代码才发现的：

- **服务没起时先红一屏 `ConnectionError`**：`/ping` 按文件名排在最后，前面 39 条集体报连接失败。改成 `pytest_collection_modifyitems` 把 `testcases/health/` 提到收集最前。
- **数据泄漏 13 条/轮**：定位到创建用例没删；修完还剩 1 条，是未认证用例清 Cookie 导致 `finally` 里恢复不了登录态。验证方式很土但有效：跑前数一次 `GET /booking`，跑完再数一次。
- **流水线自己变红**：上游 main 一提交，CI 就跑出无法复现的失败。锁 `SERVICE_COMMIT` + `requirements.lock`。
- **`--strict-markers` 只管装饰器**：`@pytest.mark.smooke` 立即报错，但 `pytest -m smooke` 拦不住——结果是 40 deselected + 退出码 5。
- **报告白屏**：`file://` 协议下数据加载失败，必须 `allure open`；另外 `reports/allure-results` 是唯一真源，命令行不要再额外传 `--alluredir`。
